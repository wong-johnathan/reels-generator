## 2. Signal, half 1 — every route except /login requires a session

### 2.1 Contract-driven unit proof

`M2` iterates the frozen `contract/api.ts` `ROUTES` table: **every** route with
`auth: true` is rejected (401, `unauthorized`) with no cookie. `M1` asserts the
middleware's public list is _exactly_ the contract's `auth:false` set, so a new
contract route cannot silently become public:

```
✓ src/web/middleware/auth.test.ts (16 tests)
  ✓ derives the public allowlist from the contract and nothing else
  ✓ rejects every contract route that says auth:true when no cookie is present
  ✓ also rejects routes that are not in the contract at all (no route enumeration)
```

## 5. Decisions, deviations and follow-ups

Decisions (recorded here rather than silently made):

1. **argon2id library:** `hash-wasm` (pure WASM) rather than a native binding, so
   `npm ci` and the images behave identically on the DS923+ and in CI, with no
   node-gyp toolchain in the build stage. Parameters are the design's, pinned by
   test.
2. **CSRF token storage:** derived as HMAC-SHA256(`SESSION_SECRET`, `csrf:v1:` +
   token hash). TECH_DESIGN §10 asks for a synchroniser token in an httpOnly
   cookie; the contract's `SessionInfoSchema` comment calls it double-submit. A
   derived token satisfies both without adding a column to the 22-table schema:
   it is stable per session, exposed to SSR via `GET /api/session`, and dies with
   the session.
3. **Seed at web boot:** LEAD_PLAN assigns the argon2id seed to B-13; it runs in
   `startFromEnvironment()` and in `npm run auth:seed`. It never rewrites an
   existing hash (that would be the reset flow R-015-3 forbids).
4. **ElevenLabs key shape:** a bare 32-hex run is also the shape of a prompt hash,
   so the shape layer requires a credential label (`xi-api-key`, `eleven…`,
   `api_key`, `secret`, `token`). The authoritative match for the real key is the
   literal `ELEVENLABS_API_KEY` env value, which the scanner already applies.
5. **Test timeouts:** `vitest.config.ts` hook timeout raised to 180 s because
   provisioning a throwaway database and applying M-001…M-005 takes 40–90 s on
   this host (B-02 measured ~67 s for its DB suite). No test was weakened.

Follow-ups (not in this diff):

- F-02 must render `csrf_token` from `GET /api/session` into forms and send it as
  `x-csrf-token` or `_csrf`.
- The contract's `ERROR_CODES` has no `forbidden`; CSRF rejection uses HTTP 403
  with code `unauthorized`. A contract owner may want a distinct code.
- Unknown-username logins skip the argon2 verify (timing difference). The
  response is identical and the backoff applies; a dummy-hash verify is the
  hardening step if the threat model ever leaves the LAN.
- Expired `session` rows are ignored by every query and `deleteExpired()` exists,
  but Milestone A has no scheduler (R-019-4 forbids cron/timers); wire the purge
  into the B-milestone housekeeping task.
- CSRF/backoff state is in memory, matching D3's single `web` container; a restart
  clears a ≤5-minute throttle.
- Route handlers beyond the auth surface remain 404 until their cards land.

## 6. Limitations (honest, not passes)

- **No Docker daemon or compose plugin on this host.** The web image entrypoint,
  `compose up` and container healthchecks were not exercised. The _built_
  `dist/src/api/server.js` was run directly against the same PostgreSQL 16.14
  used by B-02, which is what §2 records.
- **No GitHub remote/credentials:** CI (`build.yml`) was not executed here; its
  verify job already provides `TEST_DATABASE_URL` (B-02's service container).
- The login backoff and CSRF derivation were exercised with injected clocks and
  real HTTP, but not under concurrent multi-client load (single-operator LAN).
- `deleteExpired` is tested directly; no runtime caller exists until a
  housekeeping task lands (above).
