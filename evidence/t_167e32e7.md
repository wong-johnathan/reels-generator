## Deliverables

  cost from the `image_replace` matrix row (1 image, 0 TTS, 1 render pass); `runSceneReplace()`
  executes one queued replacement: qualification gate, prompt/reference resolution, one committed
  `generation_run` (`openAttempt`) before the call, `executePersisted`, content-addressed store
  write, asset + scene repoint + run link in one transaction, then RE → stale and (only if the

- `src/db/repositories/scenes.ts` — additive: `findSceneInProject()`, `lockSceneForReplace()`

- `src/db/repositories/jobs.ts` — additive: `insertQueuedJob()`, the durable enqueue row (X-3).
- `src/workers/image-stage.ts` — additive exports only (`loadReferenceSet`, `buildImageRequest`,

- `src/db/repositories/video-stages.ts` — defect fix required by the Signal: `applyStageTransition`

## Decisions

- D1 The replacement is a one-scene job, not an IM stage re-run: `scene_id` on the job row, one
  `generation_run`, one image call. Re-running the stage would refuse to regenerate existing
  images (B-10's `persistSceneImage` only links while `asset_id` is null), which is why the
  replace needs its own write path.
- D2 Only `RE` is written stale. §4.3's row is `IM(scene), RE`; the `IM(scene)` invalidation is
  discharged by the replacement call itself, so writing the whole IM stage stale would falsely
  claim the other 16 images are stale.
- D3 The superseded asset is "orphaned but retained" as a _derived_ state
  (`scene.asset_id IS DISTINCT FROM asset.id`), not a new column: the approved schema has no
  orphan flag (TECH_DESIGN §3.2) and adding one would duplicate a fact already held by
  `scene.asset_id`. Retention (R-025) can filter on this query in Milestone B.
- D4 A prompt override travels through `lockSceneForReplace()` at enqueue time (revision bump,
  R-024), so the worker always regenerates from the committed prompt; the image is only repointed
  when the call succeeds.
- D5 `replaceSceneImage()` refuses to repoint when the scene's asset changed since the request was
  generated (`SceneAssetConflictError`): a newer image is never silently overwritten.

## Adjacent defect fixed (declared, not smuggled)

`applyStageTransition` never wrote `stale = true`. `done → stale` updated the state column but left
`stale`, `stale_cause` and `stale_at` untouched, contradicting TECH_DESIGN §4.4 step 4 and making
the Signal ("marks only the render stale") unachievable without a second, illegal writer. The fix
is four CASE branches in the existing persistence wrapper; no other module writes
`video_stage.stale`. The B-15 test asserts the written values.

## Limitations

- L1 No paid provider call anywhere: the deterministic `FakeImageAdapter` is the only image source
  in these tests.
- L2 The route handler is mounted nowhere yet: the API server still serves only the probes (B-01),
  and session auth (R-015) is S-01's card. The handler is exercised directly by the tests.
- L3 The route does not publish to BullMQ; `enqueue` is an injected port and BullMQ registration is
  B-14's follow-up. The `queued` job row is the durable record (X-3) the reconciler would pick up.
- L4 The `expected_revision` guard is enforced at enqueue only. The `job` table has no payload
  column, so a prompt edit committed between enqueue and execution is not detected by the worker
  (it regenerates from the then-current prompt). Follow-up: carry `expected_revision` on the job.
- L5 Frontend half is F-06's replace affordance; not in this diff.
- L6 DB-backed tests need `TEST_DATABASE_URL` and skip loudly without it.
- L7 The suite takes ~20 minutes wall clock on this host because each DB test provisions a fresh
  database; not a failure.
