## 3. Design decisions

1. **Immutability is structural, not conventional.** TECH_DESIGN §3.1 says
   "rows are immutable (UPDATE revoked to app role)". M-006 enforces it with a
   trigger for every role, plus a `max+1` guard and trigger-maintained
   `current_version_id`, so a second write path cannot rewrite provenance.
2. **One transaction per mint.** The service locks the `series` row
   (`SELECT … FOR UPDATE`), re-reads the current snapshot _after_ the lock, then
   inserts the version and updates the editable columns. The lock is also the
   R-024 optimistic-lock point, so a stale `revision` is a 409 rather than a
   lost update. (A single `SELECT … JOIN … FOR UPDATE OF series` was rejected:
   under EvalPlanQual it can drop the joined row when the join key itself was
   just updated, turning a conflict into a spurious "not found" — the
   concurrency test caught exactly that and drove this shape.)
3. **`changed_fields` is derived, not stored.** `series_version` stays a pure
   snapshot table; the list query uses `lag(snapshot)`, the single-version query
   uses an explicit previous-row subquery. No extra column, no drift.
4. **PATCH vs POST /versions.** PATCH is an edit: a patch that changes nothing
   is a 400 (`SeriesNoChangeError`) instead of minting a no-op version.
   `POST /api/series/:id/versions` is an explicit checkpoint (IP-02): it may
   snapshot an unchanged profile and still bumps the revision.
5. **Profile patches merge JSON objects one level** (`voice_config.speed` does
   not silently drop `voice_id`); an explicit `null` clears a nullable field.
6. **Pinning is not a state transition.** `pinStageAtStart` writes only
   `video_stage.series_version_id` (and `updated_at`); `video_stage.state`
   remains `src/domain/state-machine.ts`'s single writer (B-03 contract).
7. **Target duration** is validated as 10–180 s (integer) in the service and by
   the two DB CHECKs; 75 s is the default; 90 s is documented as a UI hint only.
   `effectiveTargetDuration` / `resolveProjectTargetDuration` implement the
   per-video override with `null = inherit series`, and `setProjectTargetDuration`
   writes it.

## 7. Limitations and follow-ups

1. **Contract vs PRD duration bounds — contradiction C-B14-1.** The frozen
   `contract/api.ts` bounds `target_duration_s` at 15–300 (in
   `SeriesProfileSchema` and in `SeriesCreateRequestSchema`/`video.create`),
   while the PRD (R-009-1) and this task's card say 10–180. PRD rev 2.4 was
   followed for validation: 10 is accepted, 181 is rejected, and
   `src/domain/series.ts` exports the response schemas with that one field at
   10–180. The executable record is the test "accepts the PRD duration floor of
   10 s (contract C-B14-1)", which also asserts that the raw contract schema
   rejects 10–14 s. Recommended resolution: the tech lead edits
   `contract/api.ts` to `min(10).max(180)` (and `video.create` likewise), then
   the override in `src/domain/series.ts` can be deleted.
2. **No Docker daemon or compose plugin on this host.** The web image entrypoint
   and `compose up` were not exercised; the built artefact was run directly
   against the same PostgreSQL 16.14 the other backend tasks used. The compose
   deploy path (and its pinned postgres image) remains unproven from B-02.
3. **`video.create` / project creation is a different card.** B-14 owns the
   duration _field_ (series value + per-video override semantics, both tested)
   but not the endpoint that creates the project; the per-video override is
   exercised through `setProjectTargetDuration`/`resolveProjectTargetDuration`
   rather than through HTTP.
4. **R-002-2's asset INSERT is B-10's write path.** B-14 provides the version id
   to pin and proves the pin survives an edit; the provenance columns on new
   assets are B-10's acceptance.
5. **`series_version` immutability is a trigger, not a privilege split.** In
   this deployment the app connects as the schema owner, so `REVOKE UPDATE` from
   TECH_DESIGN §3.1 would not bind; the trigger does, for every role. If a later
   migration introduces a separate app role, the REVOKE can still be added.
6. **Integration notes for INT-01:** B-14 changes `src/api/server.ts`
   (`createRequestHandler` gained an optional third argument — B-13's call sites
   are unchanged and its tests pass), `src/db/migrations/index.ts` (M-006) and
   `src/db/runner.test.ts` (pinned migration list), and adds `src/api/http.ts`.
   Sibling branches that also touch `server.ts` routing will conflict there.
